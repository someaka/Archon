## Bug 1: process.env mutation is permanent and process-wide

**File:** `packages/providers/src/community/pi/provider.ts`, lines 171–182  
**Severity:** Medium — stale keys persist in long-lived processes across workflow runs.

### Current Behavior

```ts
// Lines 171-182
if (piConfig.env) {
  const applied: string[] = [];
  for (const [key, value] of Object.entries(piConfig.env)) {
    if (process.env[key] === undefined) {
      process.env[key] = value;
      applied.push(key);
    }
  }
  // ...logging...
}
```

Keys injected into `process.env` are **never cleaned up**. In a long-lived Archon server, a workflow run that sets `PLANNOTATOR_REMOTE=https://...` leaves that key in `process.env` permanently. Subsequent runs with a different value (or no value) silently use the stale one.

### Fix

1. **Before the loop**, capture original values for keys that will be set:

   ```ts
   const originals = new Map<string, string | undefined>();
   ```

2. **In the loop**, save the original before overwriting:

   ```ts
   originals.set(key, process.env[key]);
   ```

3. **After `bridgeSession` completes** (or in a `finally` block wrapping the `yield*`), restore originals:

   ```ts
   for (const [key, orig] of originals) {
     if (orig === undefined) {
       delete process.env[key];
     } else {
       process.env[key] = orig;
     }
   }
   ```

4. **Scope:** The cleanup must wrap the `yield* bridgeSession(...)` call (line 480) plus all code after the env-injection block that depends on Pi session state. The `try/finally` at lines 479–491 is the natural home — extend the `finally` to include env restoration.

### Verification

- **Unit test** in `provider.test.ts`: Set `piConfig.env` to `{ TEST_PI_ENV_KEY: 'test-value' }`, verify `process.env.TEST_PI_ENV_KEY` is `'test-value'` during the session, verify it's **deleted** after `sendQuery` returns.
- **Regression test:** Verify `process.env[key]` that already existed before the call is **restored** to its original value.

### Risk Assessment

- **Low.** Cleanup runs in `finally`, so it's exception-safe. Keys only get cleaned if they were `undefined` before injection (matching the existing guard), so we never clobber user-set env vars.
- **Edge case:** If another concurrent `sendQuery` call sets the same key concurrently, the second call's cleanup may delete the first call's value. This is inherent to the "shell env wins" design and acceptable — the comment already says "we only set keys not already present."

## Bug 2: AsyncQueue.iterate() uses `next !== undefined` guard

**File:** `packages/providers/src/utils/async-queue.ts`, line 60  
**Severity:** High — if a producer pushes `undefined` (or a falsy value that coerces to `undefined`), the consumer exits early, dropping all subsequent items.

### Current Behavior

```ts
// Lines 57-71
private async *iterate(): AsyncGenerator<T> {
  while (true) {
    const next = this.buffer.shift();
    if (next !== undefined) {  // ← BUG: breaks if T = undefined | void
      yield next;
      continue;
    }
    if (this.closed) return;
    // ...wait for waiter...
  }
}
```

If `T` is `undefined` (or if `T` includes `undefined` as a member), `buffer.shift()` returns a legitimate `undefined` value that gets treated as "buffer empty" — the consumer skips it and hangs waiting for a waiter that never comes.

**Practical impact:** The current `BridgeQueueItem` type is a discriminated union (`{ kind: 'chunk' } | { kind: 'done' } | { kind: 'error' }`) — none of its members are `undefined`. So in the Pi provider's actual usage, this bug is **latent** (the guard works by accident because objects are never `undefined`). However, the AsyncQueue is a general utility at `../../utils/async-queue.ts` and should handle all `T` correctly.

### Fix

Replace the `undefined` guard with a **buffer-length check**:

```ts
private async *iterate(): AsyncGenerator<T> {
  while (true) {
    if (this.buffer.length > 0) {
      const next = this.buffer.shift()!; // safe: length > 0
      yield next;
      continue;
    }
    if (this.closed) return;
    const result = await new Promise<IteratorResult<T>>(resolve => {
      this.waiters.push(resolve);
    });
    if (result.done) return;
    yield result.value;
  }
}
```

**Why `buffer.length > 0` is correct:** The buffer is only mutated by `shift()` (in this generator) and `push()` (from the producer). After the `length > 0` check passes, `shift()` is guaranteed to return a value. The `!` assertion is safe because we just checked length.

### Verification

- **New unit test** in `event-bridge.test.ts` (where AsyncQueue tests already live):

  ```ts
  test('handles undefined values without exiting early', async () => {
    const q = new AsyncQueue<number | undefined>();
    q.push(1);
    q.push(undefined);
    q.push(3);
    q.close();

    const received: (number | undefined)[] = [];
    for await (const item of q) {
      received.push(item);
    }
    expect(received).toEqual([1, undefined, 3]);
  });
  ```

- **Regression:** Run existing AsyncQueue tests — all must still pass.

### Risk Assessment

- **Very low.** The change is a strictly more correct guard. The `length > 0` check is the standard pattern for bounded buffers. No behavioral change for the current consumers (they never push `undefined`).

## Bug 3: options-translator.ts has static Pi SDK imports at module scope

**File:** `packages/providers/src/community/pi/options-translator.ts`, lines 5–17  
**Severity:** Low — currently mitigated because `provider.ts` dynamically imports `options-translator.ts`, so the crash is deferred to `sendQuery()` time. But the file violates the lazy-loading contract and is **unsafe if anyone statically imports it from elsewhere**.

### Current Behavior

```ts
// Lines 5-17
import {
  codingTools,
  createBashTool,
  createEditTool,
  createFindTool,
  createGrepTool,
  createLsTool,
  createReadTool,
  createWriteTool,
  type BashSpawnContext,
  type BashSpawnHook,
} from '@mariozechner/pi-coding-agent';
import type { ThinkingLevel } from '@mariozechner/pi-ai';
```

The header comment in `provider.ts` (lines 17–28) explicitly warns against static Pi SDK imports. While `options-translator.ts` is loaded dynamically from `provider.ts`, the file itself has static value imports from `@mariozechner/pi-coding-agent`. If any future code does `import { resolvePiTools } from './options-translator'` statically (e.g., a re-export in `index.ts`), it would trigger Pi's `readFileSync(getPackageJsonPath())` at module load, crashing compiled binaries.

**Note:** The type-only import (`import type { ThinkingLevel }`) is fine — TS erases it. Only the value imports (`codingTools`, `createBashTool`, etc.) are problematic.

### Fix

Convert the value imports to **dynamic imports cached in module-level `let` variables**, resolved on first call:

```ts
// Remove static imports. Keep type-only import.
import type { ThinkingLevel } from '@mariozechner/pi-ai';

// Lazy-loaded Pi SDK bindings. Resolved on first call to any exported function.
// Matches the lazy-loading contract documented in provider.ts header.
let _piSDK:
  | {
      codingTools: (typeof import('@mariozechner/pi-coding-agent'))['codingTools'];
      createBashTool: (typeof import('@mariozechner/pi-coding-agent'))['createBashTool'];
      // ...etc for each factory
    }
  | undefined;

async function ensurePiSDK(): Promise<typeof _piSDK> {
  if (!_piSDK) {
    const mod = await import('@mariozechner/pi-coding-agent');
    _piSDK = {
      codingTools: mod.codingTools,
      createBashTool: mod.createBashTool,
      createEditTool: mod.createEditTool,
      createFindTool: mod.createFindTool,
      createGrepTool: mod.createGrepTool,
      createLsTool: mod.createLsTool,
      createReadTool: mod.createReadTool,
      createWriteTool: mod.createWriteTool,
    };
  }
  return _piSDK;
}
```

Then in `buildPiTool()` and `resolvePiTools()`, call `const sdk = await ensurePiSDK()` and use `sdk.createBashTool(...)` etc.

**Impact on function signatures:** `buildPiTool()` and `resolvePiTools()` currently return synchronously. They must become `async`. Since they're only called from `sendQuery()` (which is already async), this is a non-breaking change.

### Verification

- **Static import test:** In a new test file or section, attempt `import './options-translator'` and verify it does NOT trigger `@mariozechner/pi-coding-agent`'s module init. This can be validated by mocking `@mariozechner/pi-coding-agent` and checking the mock isn't called during module evaluation.
- **Regression:** Run `options-translator.test.ts` — all existing tests must pass.
- **Manual check:** Grep the codebase for any static `from './options-translator'` or `from '../pi/options-translator'` outside the test file.

### Risk Assessment

- **Medium.** Converting sync functions to async changes the call chain. All callers must `await` the result. Currently the only caller is `sendQuery()` (async), so the blast radius is contained.
- **Testing:** The existing `options-translator.test.ts` imports the module statically for testing — tests will need to `await` the newly-async functions.

## Bug 4: ensurePiPackageDirShim writes to deterministic tmpdir

**File:** `packages/providers/src/community/pi/provider.ts`, lines 49–66  
**Severity:** Low-Medium — predictable path (`/tmp/archon-pi-shim/package.json`) is a minor TOCTOU / symlink-attack surface.

### Current Behavior

```ts
// Lines 49-66
function ensurePiPackageDirShim(): void {
  const shimDir = join(tmpdir(), 'archon-pi-shim');
  const shimPkgJson = join(shimDir, 'package.json');
  if (!existsSync(shimPkgJson)) {
    mkdirSync(shimDir, { recursive: true });
    writeFileSync(shimPkgJson, JSON.stringify({ ... }));
  }
  process.env.PI_PACKAGE_DIR = shimDir;
}
```

The path `/tmp/archon-pi-shim/package.json` is deterministic. On a shared machine, a malicious user could pre-create a symlink at that path pointing to a sensitive file, and `writeFileSync` would follow it (or fail). Additionally, two concurrent Archon processes could race on the `existsSync` → `writeFileSync` sequence.

### Fix

Use `mkdtemp` for a unique temp directory per call:

```ts
import { mkdtempSync } from 'node:fs';
import { tmpdir } from 'node:os';
import { join } from 'node:path';

let shimDir: string | undefined;

function ensurePiPackageDirShim(): void {
  if (!shimDir) {
    // mkdtempSync creates a unique directory, eliminating TOCTOU races
    // and symlink-attack vectors from deterministic paths.
    shimDir = mkdtempSync(join(tmpdir(), 'archon-pi-shim-'));
    writeFileSync(
      join(shimDir, 'package.json'),
      JSON.stringify({
        name: 'archon-pi-shim',
        version: '0.0.0',
        piConfig: {},
      })
    );
  }
  process.env.PI_PACKAGE_DIR = shimDir;
}
```

**Key changes:**

1. `mkdtempSync(join(tmpdir(), 'archon-pi-shim-'))` — creates e.g. `/tmp/archon-pi-shim-Ab3Xz9/`
2. Cache `shimDir` in a module-level `let` — idempotent across calls (like the original `existsSync` check, but without the race)
3. Remove the `existsSync` check — `mkdtempSync` guarantees a fresh directory

### Verification

- **Unit test:** Call `ensurePiPackageDirShim()` and verify `process.env.PI_PACKAGE_DIR` points to a directory that exists and contains a valid `package.json`.
- **Concurrency test:** Call `ensurePiPackageDirShim()` from two concurrent contexts and verify both get the same directory (cached).

### Risk Assessment

- **Very low.** The shim directory is ephemeral (cleaned up on process exit or by OS tmpdir cleanup). The change preserves the same external behavior. The only risk is if code relied on the exact path `/tmp/archon-pi-shim` — but that path is internal and undocumented.

## Bug 5: `custom<T>()` returns `undefined as unknown as T`

**File:** `packages/providers/src/community/pi/ui-context-stub.ts`, lines 123–125  
**Severity:** Low — silent no-op for unsupported dialog types. Extensions calling `ctx.custom<SomeType>()` get `undefined` cast to their expected type, which may cause silent downstream failures.

### Current Behavior

```ts
// Lines 123-125
custom<T>(): Promise<T> {
  return Promise.resolve(undefined as unknown as T);
}
```

If an extension calls `const result = await ctx.custom<number>({ ... })`, it gets `undefined` — a type lie that can cause `TypeError: Cannot read properties of undefined` downstream with no indication of what went wrong.

### Fix

**Option A (recommended): Throw with a descriptive error.**

```ts
custom<T>(): Promise<T> {
  throw new Error(
    'custom() dialog is not supported in Archon remote UI. ' +
    'This UI method requires an interactive terminal.'
  );
}
```

**Option B: Log a warning and return a type-safe default.**

```ts
custom<T>(): Promise<T> {
  console.warn(
    '[pi extension] custom() dialog is not supported in Archon remote UI — returning undefined. ' +
    'This may cause unexpected behavior in the extension.'
  );
  return Promise.resolve(undefined as unknown as T);
}
```

**Recommendation:** Option A. Throwing is the safest choice — it surfaces the incompatibility immediately, in the extension's error handler, rather than letting the extension continue with a garbage value. Extensions that need to be Archon-compatible should catch the error or check `ctx.hasUI` before calling `custom()`.

### Verification

- **Unit test** in `ui-context-stub.test.ts`:
  ```ts
  test('custom() throws for unsupported dialog type', () => {
    const bridge = createArchonUIBridge();
    const ctx = createArchonUIContext(bridge);
    expect(() => ctx.custom()).toThrow('not supported');
  });
  ```
- **Regression:** Run `ui-context-stub.test.ts` — all existing tests must pass.

### Risk Assessment

- **Medium.** If any Pi extension currently calls `custom()` and silently relies on the `undefined` return, throwing will break it. However, this is **intentional** — the extension was already broken (getting `undefined` instead of a real value), we're just making the failure visible.
- **Mitigation:** Check Pi's extension ecosystem for `custom()` usage before merging. If found, prefer Option B with a deprecation warning.

## Bug 7: `buildResultChunk` allocates a copy via `[...messages].reverse()`

**File:** `packages/providers/src/community/pi/event-bridge.ts`, line 55  
**Severity:** Low — minor unnecessary allocation.

### Current Behavior

```ts
// Line 55
const last = [...messages].reverse().find(isAssistantMessage);
```

`[...messages]` allocates a shallow copy of the entire array, `.reverse()` mutates the copy, then `.find()` scans backward. Two operations: O(n) copy + O(n) scan.

### Fix

Replace with a reverse for-loop (or `findLast`):

**Option A: `findLast` (ES2023, supported by Bun/Node 20+):**

```ts
const last = messages.findLast(isAssistantMessage);
```

**Option B: Manual reverse scan (no runtime dependency):**

```ts
let last: unknown | undefined;
for (let i = messages.length - 1; i >= 0; i--) {
  if (isAssistantMessage(messages[i])) {
    last = messages[i];
    break;
  }
}
```

**Recommendation:** Option A (`findLast`) — it's the idiomatic modern solution, supported in all target runtimes (Bun, Node 20+), and avoids the allocation entirely.

### Verification

- **Regression:** Run `event-bridge.test.ts` — `buildResultChunk` tests must pass.
- **Performance:** No measurable difference for typical Pi transcripts (<100 messages), but it's the right pattern.

### Risk Assessment

- **Very low.** `findLast` is semantically identical to `[...arr].reverse().find(...)`. The only risk is if the runtime doesn't support `findLast` — check `tsconfig` target. Bun and Node 20+ both support it.
